# STRATEGY V2 — ゼロベース設計とロードマップ

作成: 2026-07-07。3本の調査(実証済み定量ベッティング手法/日本の競馬AI・データ事情/ML実装の落とし穴)と
リポジトリの現状監査に基づく。目的は「なるべく手間をかけずに資金を増やせる状態」への最短で正直な経路の設計。

---

## 0. 結論(TL;DR)

1. **「楽に増える」状態は存在しない。ただし「ほぼ全自動で回り、勝てるかどうかを統計的に白黒つける」状態は作れる。**
   JRAの控除率は20〜27.5%。これを超えるエッジの実在は裁判記録(回収率103〜111%)で証明されているが、
   達成者は「大量レース×大量組合せをEVフィルタで薄く広く」を機械的に回した者だけ。一発の妙手ではなく運用の勝負。
2. **現行モデルは構造的に勝てない形をしている**(オッズが最重要特徴=市場の鏡写し、無補正Harville、EV閾値1.0)。
   モデル部分は作り直す。スクレイパー・ストレージ・paper-trading基盤は正しい設計なのでそのまま活かす。
3. **最重要の方針転換: 評価指標を「バックテストROI」から「市場に対する情報量(ΔR²)」に変える。**
   ΔR² ≤ 0 なら、どんな買い方をしても長期では勝てない(算術)。これは手持ちの過去データだけで判定でき、
   組合せオッズ不要。**Phase 1 の Go/No-Go ゲート**とする。
4. **組合せ馬券の直前オッズ履歴は、JRA-VANを買っても世界のどこにも存在しない**(公式開発者フォーラムで確認)。
   自前のリアルタイム収集(現行 `paper-record` の方向)が唯一の道であり、毎週自動収集を回すこと自体が
   時間とともに他者が持たない資産(proprietary dataset)になる。

## 1. 前提となる事実(調査で確定したこと)

### 1.1 JRA 控除率(公式)

| 馬券種 | 控除率 | 備考 |
|---|---|---|
| 単勝・複勝 | 20.0% | 最も低い |
| 枠連・馬連・ワイド | 22.5% | |
| 馬単・三連複 | 25.0% | 現行システムの主戦場 |
| 三連単 | 27.5% | |
| WIN5 | 30.0% | |

JRAプラス10 は「払戻がちょうど100円になる馬券を110円にする」だけの救済策で、実効控除率はほぼ上表のまま。

### 1.2 実際に勝った者の実証記録

- **卍(大阪事件)**: 2007-09年に約28.7億円購入・約30.1億円払戻(**回収率 ~105%**)。約40ファクターの
  自作ソフトで三連複/三連単を多点EV購入、A-PAT全自動。最高裁で事実認定。
- **札幌事件**: 2005-10年に計72.7億円購入・78.4億円払戻(**毎年103〜111%**、累計+5.68億円)。
  ほぼ全レースに賭ける網羅型。ソフト無し・手動でも認定された。
- **Bill Benter(香港)**: 唯一の学術的に詳細な実録。5年中4年黒字(負け年は資金の約20%ドローダウン)。
  条件付きロジット+市場オッズとの2段ブレンド。**エッジは ΔR²=0.0178 と極小**で、それが馬券の
  組合せ(エキゾチック)で乗算的に増幅されて初めて利益になった。

共通する構造: **集中勝負ではなく、EVフィルタを通した薄く広い網羅的購入**。ただし全て2015年以前の
市場環境での実績であり、現在はより効率化している(直近研究でも日本市場は欧米より効率的で、
古典的な本命-大穴バイアスはほぼ無い)。エッジは当時より確実に薄い。

### 1.3 データの構造的制約

- **馬単・三連単・三連複・ワイドの全組合せ直前オッズの過去アーカイブは存在しない。**
  JRA-VAN の時系列オッズは単勝/複勝/枠連/馬連のみ(公式フォーラム確認)。JRDBも解決しない。
  サードパーティ製品も自前ポーリングの選択的サンプルに過ぎない。→ **自前収集が唯一の道。**
- JRA-VAN DataLab は月額約¥2,090、JV-Link は Windows 専用(取得だけWindowsで行いSQLite化する
  コミュニティツール JVLinkToSQLite / jrvltsql あり)。**特徴量の質と馬連までの時系列オッズ**のために
  Phase 2 以降で導入価値あり。
- 2025年のJRA-VAN実データ研究(arXiv:2509.14645, 2004-2023年・89万頭観測): **投票総額の約半分が
  締切前5分に集中**し、最終盤のオッズ変動に情報が残る。→ ベット(記録)は可能な限り締切直前に行う。
  スリッページは実在する大きなコスト。

### 1.4 リポジトリの現状(2026-07-07 監査)

- 検証済み成績: **2026-05-31 の1日、馬単63ベット(¥7,000)全敗、回収¥0** が唯一の実データ。
  (1ベットあたり p≈3% なら63連敗の確率は約15%あり統計的な死刑判決ではないが、下記の構造問題を
  考えると期待EVはそもそも負だった可能性が高い。)
- バックテスト +19.3% は推定オッズ由来で**信頼できない**(リポジトリ自身が明記済み)。
- 学習データ(netkeiba SQLite): 2022年 3,488 / 2023年 460 / 2024年 2,735 / 2025年 0 レース。
  JRAは年間約3,450レースなので **2023・2025 に大穴**。
- 資産として活きるもの: Rust ライブパイプライン(スクレイパー・オッズAPI・キャッシュ・タイムアウト)、
  SQLite ストレージ、paper-record/settle/report ループ、公式払戻パーサ(実HTML検証済み)。
- 作り直すもの: モデルと評価系(§2)。

## 2. なぜ今のままでは勝てないか(現行システムの構造的問題)

1. **市場の鏡写しモデル。** 現行デプロイモデル(CatBoost)はオッズが重要度1位(23%)の特徴量。
   容量の大きいGBDTにオッズを直接food すると市場のランキングを再現するだけになり、
   「市場が知らないこと」= エッジを分離できない。Benter が明示的に否定した設計。
   (皮肉なことに、その前の LightGBM はオッズを無視して壊れていた。両極端を経験済み。)
2. **無補正 Harville。** Harville 公式は本命馬の2着・3着確率を系統的に過大評価する(文献で確立)。
   馬単・三連単の確率がすべて歪む。Benter は指数補正(γ≈0.8, δ≈0.65 相当、市場ごとに要フィット)を
   MLE で当てて初めて使い物にした。
3. **EV閾値 1.0 + 推定誤差 = 勝者の呪い。** EVフィルタは「モデルが最も過大評価した組合せ」を
   優先的に選ぶ。閾値をちょうど 1.0 に置くと、選ばれるのはほぼ推定誤差。
4. **検証不能な馬券種から始めている。** 三連単のエッジを統計的に検証するには(的中率1-2%・
   配当の裾が重いため)数万〜数十万ベット必要。単勝なら千件弱、ワイド/馬連なら数千件で足りる。
   高控除率(25-27.5%)かつ検証不能な馬単・三連単を主戦場にするのは順序が逆。
5. **評価指標がROI。** 少サンプルROIはほぼノイズ(2000%回収率が外れ値2発だった実例あり)。
   モデルの良し悪しは市場対比の対数尤度(ΔR²)で測るべきで、これはROIより桁違いに低分散。

## 3. 勝てる設計(ターゲットアーキテクチャ)

エビデンスが支持する唯一のアーキテクチャは Benter 型。各段を現代の道具で置き換える。

```
[特徴量: オッズを含まない]                       [市場: 直前オッズ]
        │                                              │
        ▼                                              ▼
(A) ファンダメンタルモデル                    π_i = 市場込み確率(控除率除去)
    LightGBM/CatBoost per-horse score                  │
    → レース内 softmax で f_i                          │
        │                                              │
        └────────────┬─────────────────────────────────┘
                     ▼
(B) 2段ブレンド(パラメータ2個のロジット、ホールドアウトでMLEフィット)
    c_i = softmax(α·log f_i + β·log π_i)
                     ▼
(C) 着順分布 → 組合せ確率: 補正付き Harville
    (γ, δ を自データの着順で MLE フィット。無補正禁止)
                     ▼
(D) ベット選択: EV = c × 組合せオッズ > 閾値(1.1〜1.2 から開始)
    + 極端な大穴除外(モデル確率 < 下限のものは買わない — Bolton-Chapman 以来の再現知見)
                     ▼
(E) サイジング: 1/4〜1/2 Kelly + 連敗確率の上限制約(エキゾチックは低的中率)
```

### 3.1 モデル(A): オッズフリー・ファンダメンタル

- **特徴量からオッズ・人気を完全排除**。現行39特徴のうちオッズ系を除いたものが出発点。
  強化候補: 走破タイム系(スピード指数)、上がり3F、コーナー通過順から脚質、クラス昇降、
  騎手×コース成績、休養日数、斤量変化、血統(既存インフラあり)。
- 学習目標はレース内相対評価: LightGBM `lambdarank` または着順の listwise(Plackett-Luce 的)学習
  → スコアをレース内 softmax。二値分類(勝ち/負け)単体より着順全体を使う方が1レースあたりの
  情報量が多い(Bolton-Chapman 以来の定石)。
- 温度スケーリング等のキャリブレーションは**レース内正規化後**に当てる(合計1制約が本質)。

### 3.2 評価(B の前後): ΔR² が唯一の Go/No-Go 指標

```
R²_market   = 市場オッズのみで着順(勝者)を説明する擬似R²(対数尤度ベース)
R²_combined = ブレンド後 c_i での擬似R²
ΔR² = R²_combined − R²_market
```

- **ΔR² > 0 が安定して出ないなら、いかなる買い方でも長期で勝てない。** 逆にBenterは ΔR²=0.018 で
  5年勝った。目標は「まず正の ΔR² を作る」こと。ROIはその後の話。
- 必要データは**着順と単勝オッズだけ**(手持ちの過去データで計算可能)。walk-forward
  (年単位で学習→翌年評価)で年ごとの ΔR² を出す。
- 注意: 過去データの単勝オッズは「最終」オッズで、実際にベット時点で見られるオッズより
  情報が多い(直前5分に投票の半分が入る)。したがって歴史データ上の ΔR² は楽観側。
  ライブでの再確認(Phase 3)まで割り引いて解釈する。

### 3.3 データ戦略

1. **即時(無料)**: netkeiba 歴史スクレイプの完全化 — 2023 の欠損(~3,000レース)、2024 の残り
   (~700)、2025 全年(~3,450)。合計 ~13,800 レースの学習セットに。既存 `scrape-historical` で可能。
2. **毎週(無料・最重要)**: **全レースの直前オッズ自動アーカイブ**。paper-record が今やっていることを
   「予測なしでも全レースで」回し、単勝+馬連+馬単(+可能なら三連複)の組合せオッズを締切前に
   スナップショット。これが誰も持っていない検証用データセットに育つ。
3. **Phase 2 以降(有料判断)**: JRA-VAN DataLab(月額 ~¥2,090 + Windows VM)。得られるもの:
   調教・馬場詳細などの特徴量の質、馬連までの公式時系列オッズ、クリーンな結果データ。
   **ΔR² ゲートを通過してから**購入する(通過しないなら払う意味がない)。

### 3.4 馬券種ポートフォリオ(検証と収益化を分離する)

| フェーズ | 馬券種 | 理由 |
|---|---|---|
| モデル検証 | (賭けない)ΔR² | オッズ不要・最低分散 |
| 戦略検証(paper) | 単勝・馬連・ワイド | 控除率20-22.5%、的中率が高くCIが数百〜数千件で収束 |
| 収益化(実弾) | + 馬単・三連複 | エッジ実証後、乗算増幅を取りに行く。三連単は最後(27.5%+検証不能な分散) |

現行の paper インフラは馬単・三連単のみ対応 → 単勝/馬連/ワイドのオッズ取得・払戻パースを追加する。

### 3.5 運用(「楽に」の実装)

ユーザーは競馬に興味がない前提で、**人が判断するポイントをゼロにする**:

- 開催日の朝: cron がその日のレース一覧と発走時刻を取得(`race.netkeiba.com`)
- 各レース締切 2〜5 分前: 自動で オッズ収集 + paper-record(スリッページ最小化のため直前)
- 夕方: 自動 paper-settle(race.netkeiba は即時公開 — 対応済み)
- 週次: paper-report + **統計サマリ(ROI の95%信頼区間、ベット数、ΔR² 追跡)** を自動生成
- macOS 常時稼働が制約になるなら、この収集デーモンだけ安価なVPSに置く選択肢あり

実弾投票(IPAT自動化)は技術的に可能で事実上黙認されている(裁判の当事者もA-PAT自動購入)が、
公式APIはなくToS保護もないグレー領域。**paper で正のエッジが統計的に確認できるまでスコープ外**。
確認後も、まず手動投票(週末のみ・数分)→ 半自動(netkeiba IPAT連携)→ 自動化の順で段階導入。

## 4. ロードマップ

各 Phase に **Go/No-Go ゲート**を置く。ゲートを通らなければ次に進まず、撤退判断も明文化する。
(これは「ダラダラ資金と時間を溶かす」ことを防ぐための、このプロジェクトで最も重要な規律。)

### Phase 0 — 土台のリセット

- [ ] 評価ハーネス: walk-forward で R²_market / R²_combined / ΔR² を計算する Python モジュール
      (入力: 着順+単勝オッズ。既存 SQLite + Kaggle データで動く)
- [ ] netkeiba 歴史データ完全化(2023 残り / 2024 残り / 2025 全年)→ ~13,800 レース
- [ ] ベースライン計測: 「市場オッズのみ」の R²_market を確定(以後の物差し)

### Phase 1 — オッズフリー・ファンダメンタルモデル

- [ ] オッズ・人気を特徴量から排除した新モデル(lambdarank / listwise → レース内 softmax)
- [ ] 特徴量拡充(スピード指数、脚質、騎手×コース、クラス移動、血統)
- [ ] 2段ブレンド(α, β の MLE フィット)を実装し、年ごとの ΔR² を計測

**GATE 1: 直近2年以上のホールドアウトで ΔR² > 0 が安定して出ること。**
出ない場合 → 特徴量強化(JRA-VAN 導入の前倒し検討)で1回だけ再挑戦。それでも 0 なら、
このデータセットでは市場超過情報が作れていないという事実を受け入れ、実弾展開はしない。

### Phase 2 — 組合せ確率とベットエンジン

- [ ] Harville 補正(γ, δ を自データの2着・3着実績で MLE フィット、Rust 側にも移植)
- [ ] 単勝・馬連・ワイドのオッズ取得+払戻パース追加(paper 基盤拡張)
- [ ] EV 閾値 1.1〜1.2・大穴除外・1/4 Kelly +連敗制約のベットエンジン
- [ ] (任意)JRA-VAN 導入: Windows VM + JVLinkToSQLite、特徴量と馬連時系列オッズ

### Phase 3 — 全自動 paper-trading とデータ資産化

- [ ] 開催日フルオート: レース発見 → 締切直前オッズ収集(全レース・予測対象外も)→ record → settle → 週次レポート
- [ ] レポートに統計を組み込む: ROI 点推定 + 95%CI、馬券種別、スリッページ(記録時 vs 最終オッズ)分析
- [ ] ライブ ΔR² 追跡: ベット時点オッズでの市場対比(歴史データの楽観バイアスを補正した真の値)

**GATE 2: 単勝/馬連/ワイドで累計 1,000+ paper ベット、ROI 点推定がプラス、かつライブ ΔR² > 0。**
(1,000件は最低ライン。CI が控除率負けを否定できるまで実弾は張らない。)

### Phase 4 — 小額実弾

- [ ] 週末のみ・手動投票から開始(paper と同一のベット指示を出すだけの状態にしておく)
- [ ] バンクロール規律: 総資金の上限を先に固定、1/4 Kelly、月次ドローダウン上限(例: -30%で停止・再検証)
- [ ] paper と実弾の乖離(スリッページ実測)を毎週レビュー
- [ ] 乖離が許容内なら netkeiba IPAT連携 → 自動化を段階検討

### 継続運用

- 再学習: 開催シーズンごと(walk-forward と同じ粒度)。ΔR² が2期連続で劣化したら停止して調査
- オッズアーカイブは無条件で回し続ける(モデルが死んでもデータは資産)

## 5. 現実的な期待値と撤退条件(正直な話)

- **達成可能な上限の目安**: 史上最良の実録(Benter)でも市場超過情報は ΔR²=0.018、現実的なROIは
  数%〜10%程度。裁判の勝者たちも 103〜111%。「回収率150%」の類いは全てリーク・外れ値・広告。
- **勝っていても負ける期間が必ずある**: Benter は本物のエッジ+分数Kellyでも 5年中1年は -20%。
  数ヶ月の赤字はエッジの否定にならず、数ヶ月の黒字はエッジの証明にならない。判断は常にCIで。
- **最頻の失敗はモデルではなく検証**: リーク(レース後情報・最終オッズ)、少サンプルROI信仰、
  スリッページ無視。本設計のゲート構造はこれらを潰すためにある。
- **撤退条件(先に決めておく)**:
  - GATE 1 を2回失敗 → 実弾はしない(オッズアーカイブだけ趣味的に続けるかは任意)
  - GATE 2 で CI が控除率負けを否定できない → Phase 4 に進まない
  - 実弾で月次ドローダウン上限到達 → 停止し、paper に戻って再検証
